# 反馈闭环规范(user-question.md ↔ TODO.md)

## 1. 反馈入口:user-question.md

- 位置:`docs/harness/user-question.md`(随本目录统一管理)
- 用户的任何问题/愿景,第一时间记入该文件,**按轮次分节**,已完成的反馈**不删除**,保留历史
- 每条反馈三要素:问题现象(现状痛点)、愿景(想要什么)、可参考(如"参考 cc switch")

### 格式模板

```markdown
## 第 N 轮(YYYY-MM-DD)

> 状态:🔄 进行中(或 ⏳ 待处理 / ✅ 已完成(vX.Y.Z))

### N. 反馈标题

问题现象:...
愿景:...
可参考:...(可选)

> ✅ vX.Y.Z 交付:一句话说明做成了什么(完成后回填)
```

## 2. 版本更新流程(强制顺序)

1. **读取**:AI 启动新版本开发前,必须通读 user-question.md 中所有 ⏳/🔄 条目
2. **确认**:逐项与用户确认关键决策点——用选项式提问(推荐项放首位并标注 Recommended),记录用户的最终选择;未确认的条目不允许动手
3. **生成 TODO.md**:
   - 勾选式(`- [ ]`),按实施顺序分节
   - 头部记录:来源(user-question.md 第几轮)、本轮已确认的设计决策、实施顺序
   - 每节末尾包含验证项(typecheck / build / 接口 / UI 实测)
4. **实施**:逐项完成,每项完成立即验证并勾选(不允许攒到最后一起勾)
5. **回标(前先重读)**:回标前必须**重读 user-question.md 全文**——用户在闭环进行中可能追加新条目(第 5 轮 #13 即因此漏掉一轮),确认无遗漏后才允许勾选收尾。
   - TODO.md:所有项 `- [x]`
   - user-question.md:对应条目追加 `> ✅ vX.Y.Z 交付:...`,轮次状态改为 ✅ 已完成
   - CHANGELOG.md 记录本版本;README 功能全景表同步

## 3. TODO.md 规范

- 位置:仓库根目录 `TODO.md`(用户可直接查看进度)
- 结构:来源说明 → 已确认决策 → 分节任务(每节含验证项)→ 收尾项
- 追加迭代:新反馈生成新分节,附在已有内容之后,不覆盖历史

## 4. 反例(禁止)

- ❌ 不看 user-question.md 直接凭印象开发
- ❌ 用户说"大概这样"就动手,不确认关键取舍
- ❌ 完成后只勾 TODO,不回标 user-question.md
- ❌ 删除或改写已完成的反馈条目(应追加 `> ✅` 回标,保留原文)
