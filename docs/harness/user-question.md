### 2. 实时活动流重复展示同一条助手消息

问题现象:同一条 Codex 助手消息会连续出现两次,时间和内容完全相同。接口复核发现它们被保存为两个不同 seq 的事件,不是单纯的前端重复渲染;本轮多条助手消息均可稳定复现。

愿景:按来源事件 ID 或稳定指纹在入库前去重,并兼容清理已有重复记录,保证一条真实消息在活动流中只出现一次。

> ✅ v0.3.4 交付:入库按(agent+会话+类型+全文)指纹去重——发射路径与文件监听路径同一条消息只入库一次;一次性迁移清理存量重复 1415 条。实测消息类相邻重复为 0。

### 3. 内部注入上下文混入用户可见记录

问题现象:实时活动流和「发任务」抽屉的任务记录会把 `<recommended_plugins>`、系统提醒、运行时上下文、协作约定以及拼接后的 `[对话背景]` 当作普通用户消息完整展示。真实任务描述被这些内部内容淹没,也让用户误以为自己发送过这些文本。

愿景:展示层区分「用户原始输入」与「系统注入上下文」。默认只显示用户本轮真实消息;内部上下文如确有排障价值,放入明确标注的可折叠调试详情,并对可能包含的敏感信息做脱敏。

> ✅ v0.3.4 交付:①四工具解析器过滤 <recommended_plugins>/<system-reminder> 等系统注入,不再生成用户消息事件;②[对话背景]注入任务在展示层自动提取「[本轮消息]」之后的真实输入(活动流/会话标题/任务记录);③任务记录改用用户原始输入。dsh/claude 索引已重建。

问题现象:四个特工当前合计已有 177 个会话,但会话档案只请求并显示最新 100 条,页面没有「加载更多」或分页入口;搜索和特工筛选也只作用于这 100 条已加载数据,较早会话实际无法查找。

> ✅ v0.3.4 交付:会话档案服务端分页(游标「加载更早」),头部显示「已加载 X / 共 Y」;搜索与特工筛选下推服务端,覆盖全部会话。

### 5. 空会话与测试数据挤占会话档案

问题现象:会话档案顶部存在大量标题仅为会话 ID、项目为「—」、消息数为 0 的记录,有效会话很快被挤到下面;同时还残留明显的测试记录,例如 `01a88888-aaaa-7bbb-cccc-dddddddddddd` 和「watcher测试回复2」,其时间还显示为未来的 08/16 05:12。

愿景:默认隐藏或单独归档 0 消息会话,提供「包含空会话」筛选;测试产生的数据验证后自动清理,异常未来时间应标记或纠正,避免污染真实档案排序。

> ✅ v0.3.4 交付:默认隐藏 0 消息空会话并提供「含空会话」开关;清理残留测试文件与记录(01a88888 等);修复 claude/dsh「已消费文件重启后汇总清零」的历史 bug 并重建索引,档案总数从虚高的 177 收敛为真实数据。

## 第 4 轮(2026-08-16)

### 1. 明确项目的求职定位与简历口径

问题现象:OpenHarness 已实现四种 AI Coding Agent 的统一接入、任务控制、会话索引和实时观测,但如果笼统包装成“自研 Agent 框架”,容易让面试官误以为项目实现了模型层的 Planning、Tool Calling 或 ReAct Runtime;如果只写成“个人控制台”,又会低估其中的 Agent 工程价值。

愿景:将项目统一定位为“多 Agent 编排与可观测控制台”或“AI Coding Agent 控制面”。对外明确说明项目不重新实现模型层 Agent,而是通过原生 CLI 和本地会话数据解决异构适配、任务生命周期、会话状态、实时观测和安全边界问题。简历中与 WeCare RAG 项目形成互补:WeCare 证明 LLM/RAG 落地能力,OpenHarness 证明 Agent 工程与 TypeScript 全栈能力。

建议简历标题:`OpenHarness 多 Agent 编排与可观测平台｜独立项目`。

## 第 5 轮(2026-08-16)

> 状态:⏳ 待确认(决策点待用户逐项拍板,未动手)

### 1. 跨 Agent 派活的安全与可靠性缺口

问题现象:审查「协作约定」派活链路(packages/server/src/conversations.ts:220-222)发现四个具体缺口:

1. 注入的协作约定硬编码 `"bypassPermissions":true`——用户在 UI 未勾选「完全自主」,但 Agent 间互派的子任务默认全自主执行,违背「完全自主类开关默认关闭」红线;且 tasks 表不存该字段(store.ts:62-72),事后无从追溯哪些任务跑在自主模式;
2. 协作约定硬编码端口 `3900`,修改 `OPENHARNESS_PORT` 后约定指向的 API 失效;
3. `/api/tasks` 无鉴权,本机任意进程可发起全自主任务(与仅监听 127.0.0.1 的定位勉强自洽,但调用方式被注入进发给任意 LLM 的 prompt,攻击面被放大);
4. `queue=true` 的任务出队接续时只带 `{cwd, prompt}`(packages/server/src/tasks.ts:192),丢失 `conversationId / resumeSessionId / bypassPermissions`,且 prompt 被替换为展示文案(tasks.ts:125)——带 conversationId 的派活一旦撞上该 Agent 正忙而排队,结果回流归因直接断链。

愿景:子任务权限与用户 UI 开关一致;协作约定端口动态生成;排队任务按原始参数原样接续;bypassPermissions 落库可追溯。

决策点:

- A. 协作约定里的 bypassPermissions 取值:
  - (Recommended) 透传用户当前「完全自主」开关状态(默认关),子任务权限与用户选择一致
  - 固定为 false,需要自主时用户在对话里显式开启
  - 维持 true 不改(派活效率优先)
- B. `/api/tasks` 是否加鉴权:
  - (Recommended) 本轮不加,维持仅本机监听定位,在 architecture.md 安全边界一节明确标注该风险
  - 加轻量 token(服务启动生成,协作约定携带,请求头校验)
- C. bypassPermissions 落库方式:
  - (Recommended) tasks 表加列(经 PRAGMA table_info 检查迁移),任务记录与对话气泡展示「完全自主」标记
  - 不落库,仅事件 meta 携带(重启后不可追溯,维持现状)

### 2. 多 Agent 协同闭环(Supervisor 编排层启动方案)

问题现象:当前跨 Agent 派活是 fire-and-forget——A 派活给 B 后 A 的任务即结束,B 的结果只回流成本对话气泡(conversations.ts:178-195 仅更新气泡),没有任何机制自动唤醒 A 消费结果;想要闭环只能靠 Agent 自己轮询 API(烧 token)或人做中转。对话室一次也只能派给一个 Agent(send 的 agent 为单值参数),无并行分工、依赖、聚合。第 4 轮 #6 已把 Supervisor 编排层记入 Roadmap v0.7 候选,但"回收结果"环节尚无实现方案。

愿景:分阶段补齐协同闭环——先让"派活→结果→自动回到委派方继续"成环,再考虑多步计划编排;全程保留人在环与完整 Trace,不破坏「Wrap, don't replace」原则。

决策点:

- A. 起步范围(后续阶段可递进):
  - (Recommended) L2 回调闭环:子任务 task-end → 服务端自动以结果 resume 委派方 Agent(注入子任务产出作 prompt),最小改动补上 #6 提案缺失的"回收"环节
  - L1 显式编排 API:一次提交结构化多步计划(步骤+依赖+聚合),经用户确认后执行
  - L3 协作协议工具化:把协作约定从自然语言升级为 MCP 工具(delegate/wait/query),类型化、可审计
  - L4 会话级共享黑板:结构化共享状态,不再只靠聊天气泡
- B. 自动执行门槛:
  - (Recommended) 默认人在环:编排计划需用户确认后执行,设扇出/深度/成本上限,自动执行默认关闭(对齐安全红线与 #6 提案)
  - 提供显式红色警示开关,允许可信目录下全自动
- C. 对外命名口径:
  - (Recommended) 沿用「Supervisor 编排层」,不包装成"Multi-Agent 协作平台"(docs/resume-bullets.md 明确警告过)
  - 对外称「多 Agent 协同」



## 第 5 轮(2026-08-16)

> 状态:⏳ 待处理
> 来源:对标 Clowder AI(github.com/zts212653/clowder-ai)后,筛选出可直接借鉴、且不违背"本地优先/一个页面/轻依赖"原则的部分。

### 1. @mention 显式路由(对话室)

问题现象:当前对话室靠顶部特工 chips 切换 Agent,切换动作与消息发送分离;一条消息只能发给一个特工,无法在消息里显式点名。

愿景:借鉴 Clowder 的 @mention 路由——输入框消息中包含 `@小克` / `@码星人` 等时,自动切换该特工并发送;支持一条消息 @多个特工(每个特工各收到一份带各自上下文的任务)。轻量实现:解析 @特工名 前缀,复用现有切换+摘要注入机制,不改数据模型。

### 2. 跨模型评审(内置互审)

问题现象:目前"让另一个 Agent 审"需要手动切换、手动写"请评审…"指令,没有结构化入口。

愿景:借鉴 Clowder 的内建跨模型评审(Claude 写、GPT 审)。轻量实现:助手气泡旁增加「送评审」按钮——弹出特工选择,自动注入对话摘要 + 评审指令(正确性/风险/改进点)并派发任务,评审结果回流本对话。

### 3. Agent 角色设定注入(持久身份)

问题现象:四个特工的漫画风角色(小克/光标侠/码星人/鲸酱)只存在于界面展示层,Agent 实际执行时对自己的角色一无所知,回复风格不稳定。

愿景:借鉴 Clowder 的持久身份——为每个 Agent 定义一段简短角色卡(职责/风格/边界),任务发射时作为 system 上下文注入(只注入一次,不重复累加);角色卡存于 OpenHarness 本地数据,可在配置页编辑。

### 4. 富文本渲染升级(rich blocks)

问题现象:Markdown 渲染已支持标题/列表/代码块/表格,但 Agent 常输出流程图(mermaid)与数学公式(LaTeX),目前以原文展示;代码块无复制按钮。

愿景:借鉴 Clowder 的 react-markdown + KaTeX + Mermaid——轻量补:mermaid 代码块渲染 + KaTeX 数学渲染 + 代码块「复制」按钮。保持 marked+DOMPurify 消毒链路不变,按需引入 mermaid/katex(懒加载,不增加首屏体积)。

### 5. 共享记忆(团队记忆)

问题现象:切换 Agent 时只注入最近 6 轮摘要,跨会话的"经验教训/决策记录"无处沉淀,每次新对话都从零开始。

愿景:借鉴 Clowder 的共享记忆(evidence store / lessons learned)——轻量实现:本地一份"团队记忆"文档(~/.openharness/memory.md),对话室提供「记一笔」入口(把当前结论追加进去);切换/新对话注入摘要时附带上最近 N 条记忆。保持纯本地、纯文件,不引入向量库。

### 6. 费用看板(quota board)

问题现象:用量账本只有 tokens 与工具调用数,没有费用;与 Roadmap v0.6 的"费用估算(可配置价目表)"重合。

愿景:借鉴 Clowder 的 Quota Board(实时 token 用量与成本)——实现 Roadmap v0.6 费用估算时,以它为参考:可配置各模型价目表、用量账本实时折算费用、按特工/项目聚合展示。

### 7. 特性生命周期状态板(可选,较大)

问题现象:一个对话往往对应一个特性/任务,但没有阶段追踪(想法→方案→进行中→评审→完成),多对话并行时容易失控。

愿景:借鉴 Clowder 的 Mission Hub(特性生命周期 + 公告板)。若做,先做最小版:对话记录列表支持阶段标签(手动设置 + Agent 可建议),活动流按阶段筛选;Need Audit(PRD 自动拆解)与公告板暂不引入。
